# v0.1.0 设计文档：代码清理与 Backpack 用户数据流

**日期**: 2026-01-16
**版本**: 0.1.0
**目标**: 清理无关交易所代码，专注 Aster + Backpack，添加 Backpack 用户订单成交流

---

## 项目背景

准备运行 Aster XAU 与 Backpack PAXG 之间的套利策略，需要验证架构是否合适。当前代码库包含 Hyperliquid 和 Lighter 的实现，但这两个交易所暂不使用。将其归档以简化代码库，作为 0.1.0 版本发布。

同时，套利策略需要实时监控订单成交状态，而当前 Backpack 只有订单簿 WebSocket，缺少用户数据流。需要添加 `BackpackUserWS` 来订阅私有订单成交事件。

### 二、Backpack 用户数据流实现

#### 2.1 功能需求

**订阅内容**:
- 订单状态更新（新建、部分成交、完全成交、取消）
- 订单成交明细（价格、数量、手续费、maker/taker）
- 账户余额变化（可选）

**认证方式**:
- 使用 API Key + Secret 进行签名认证
- 参考 Backpack REST API 的 Ed25519 签名方式

**统一事件格式** (与 Aster 保持一致):
```python
{
    "exchange": "backpack",
    "stream": "user",
    "event_type": "order" | "trade" | "account",
    "ts_exchange": <timestamp_ms>,
    "ts_local": <timestamp_ms>,

    # 订单更新字段
    "type": "order",
    "symbol": "PAXG_USDC_PERP",
    "order_id": "123456",
    "client_order_id": "my_order_1",

    "avg_price": "2000.5",

    "last_qty": "0.5",
    "last_price": "2000.5",
    "is_maker": true,
    "fee": "0.001",
    "fee_asset": "USDC",

    "raw": {...}  # 原始消息
}
```

#### 2.3 实现注意点

1. **认证机制**: 需要查阅 Backpack WebSocket 文档确认认证方式
2. **保活机制**: 检查是否需要定期 ping 或续期
3. **错误处理**: 认证失败、订阅失败的重连逻辑
4. **消息解析**: 将 Backpack 原始格式转换为统一格式
5. **与 Aster 一致性**: 保持事件字段命名和结构一致

1. **Backpack API 文档不全**: 可能需要抓包分析 WebSocket 协议
2. **认证方式差异**: WebSocket 认证可能与 REST API 不同
3. **保活机制**: 不确定 Backpack WebSocket 超时策略

**缓解措施**:
- 参考官方文档和社区实现
- 使用浏览器开发者工具抓包分析
- 实现灵活的重连和保活机制
